# 阶段四：长上下文（block_size 128 → 512）

> 状态：计划就绪，未开跑。前提：阶段三（**新数据，vocab 6027**）1 万步结果落定（总表填完 + commit）。

## 回答的问题

**同样的数据量（token 数）下，512 上下文是否比 128 更好？**
其余全部与阶段三相同（8 层 / 128 维 / ffn 256 / 4 头 / batch 64 / 同调度 / seed 42 / 无 GQA）。

## 为什么这次改动的代价极低（阶段三的兑现）

逐行核实，模型代码**零改动**：
- `model.py:97` `precompute_freqs_cis(head_dim, end=config.block_size)` —— RoPE 表长度跟随 config
- `model.py:107` `cos = self.freqs_cos[:T]` —— 按实际长度切片
- `model.py:142` `idx[:, -self.config.block_size:]` —— generate 已按窗口截断
- `Dataset.py`：block_size 是构造参数，切窗自动跟随

→ 上下文长度从"架构改动"降级为"改一个数字"。附带好处：RoPE 无参数，参数量保持 1,829,376（@6027；若用学习式位置表则要多 512×128 = 65,536 参数）。

## 步数设计（token 对齐，受控关键）

- block 512 × batch 64 = 32,768 token/步（阶段三是 8,192）
- **2500 步 × 32,768 = 81.9M token = 阶段三的 10,000 步**（= 新训练集的 ≈2.17 epoch，两边一致）
- attention ∝ T²，每步重约 2.6 倍，但步数是 1/4 → 总耗时 ≈ 阶段三 1 万步的 2/3
- 对比锚点：**最终对最终**（两边都是 81.9M token 训完），中间曲线看各自日志

## 代码改动（只有两处）

1. `model/Config.py`：
```python
vocab_size = 6027   # 数据更新（阶段三重跑时已改；若沿用其配置，此处不动）
block_size = 512    # 原 128
epochs = 2500       # token 对齐阶段三的 10000
```
（其余全部不动：n_layer 8 / n_embd 128 / b_head 4 / batch 64 / warmup 200 / base_lr 1e-3 / min_lr 1e-4 / clip 1.0 / seed 42）

2. 新文件 `eval_ppl.py`（统一最终评测协议，100 batch）：
```python
import math
import torch
from model.model import GPT
from model.Config import GPTConfig
from Dataset import MyDataset

# —— 每次跑改这两行 ——
CKPT = "checkpoints/phase4_final/step_latest.pt"
BLOCK = 512        # 必须等于该 checkpoint 训练时的 block_size

config = GPTConfig()
config.block_size = BLOCK
gpt = GPT(config).to(config.device).eval()
state = torch.load(CKPT, map_location=config.device)
sd = state["model_state_dict"] if "model_state_dict" in state else state
gpt.load_state_dict(sd)

ds = MyDataset("data/val.bin", config.block_size, config.batch_size)
N = 100
losses = []
with torch.no_grad():
    for _ in range(N):
        x, y = ds.get_batch(config.device)
        _, loss = gpt(x, y)
        losses.append(loss.item())
val = sum(losses) / len(losses)
print(f"{CKPT}\nval loss = {val:.4f}   PPL = {math.exp(val):.2f}   (100 batches, block={BLOCK})")
```

`train_mini.py` 不用改：val 每 100 步 20 batch，512 窗口下每次估算 65 万 token，比阶段三更稳，开销占比不变（~20%）。

## 预检（开跑前 1 分钟）

- `checkpoints/step_latest.pt` 必须不存在（从零开始）；**旧数据 checkpoint（4242 维度）全部作废**，移入 `checkpoints/old_4242/` 留档，防止误加载（加载即形状不匹配，不会静默出错）
- `test_train1.py` 的 x 形状改 `(2, 512)` 跑一遍：期望同指纹（loss 90~110，argmax==x ≈1.0，该指纹与词表大小无关）→ 证明 512 的 RoPE 表工作正常
- 显存：64×512，峰值约 4~6GB（logits 张量 64×512×6027×4B ≈ 0.79GB 是大头）；若 OOM → batch 32 + epochs 5000（token 数不变）

## GQA 为什么不在本阶段

GQA 的真实价值（KV 减半、长上下文生成加速）以存在 KV cache 为前提；当前 `generate()` 无 cache，此时上 GQA 收益微小 → 挪到阶段五（与 KV cache 一起，收益才兑现）。
